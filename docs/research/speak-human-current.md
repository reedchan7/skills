# 说人话 · 当前实现与实测结果

当前发布版本：`speak-human`，`metadata.version: "1.0.0"`。按用户要求，将完成简洁性和结构调整后的版本统一定为初始版本 1.0.0；下文评测文件中的版本号和哈希保留为当时的开发记录。

## 当前版本的本机安装

已通过仓库同步脚本安装到 `~/.agents/skills/speak-human` 和 21 个 Agent 技能目录；逐项比对正文，版本均为 1.0.0，内容哈希一致。Antigravity 的各入口使用真实目录、内部文件链接的布局。

Claude、Codex、Grok、Gemini、Kimi、OpenCode、OpenClaw、Pi、Reasonix 共 9 个运行时已实际识别；Claude 进一步调用了 Skill，返回正文与当前发布文件完全一致。其余入口完成文件及布局核对。详见[当前安装记录](../../evals/speak-human/results/install-current.json)。已有会话可能缓存技能清单，新开会话可重新加载。

## 当前规则：篇幅与结构分别判断

用户进一步明确：说人话后仍有一定长度的回答，需要金字塔式组织、章节、顺序和层次。先筛选必要内容，再按剩余内容选结构：一个短要点直接成段；几个并列要点分点；多个问题、论证或阶段分章节，按“结论→支撑要点→必要证据”组织。同层按同一逻辑归类，因果解释按因果、操作按依赖顺序、方案按共同的关键维度比较。

结构不能增加无用内容，简洁也不能把多个层次挤成一段。下面的1.0.1及1.0.0实测记录仍属于各自开发快照，以文件哈希区分，不能仅凭版本号视为当前发布版本的评测。

## 根据用户实际阅读反馈修正

用户指出展示样例明显变长。此前把原回答的节选与完整材料的扩写放在一起比较，既不公平，也偏离“不啰嗦”的目标。模型偏好票不能替代用户的阅读感受。

本次将“完整”限定为足够回答眼前的问题：单个聚焦问题先用2—4个完整句子给出答案和决定性的原因/条件，不自动增加测试清单、备选方案、背景或下一步。确有必要的信息或明确要求的详细说明不受这个起始篇幅限制。结构只组织必要内容；理论支撑通常用一句因果说明即可。短文改写默认保持原有范围，完整交接等明确要求仍须保留全部操作条件。

下方模型评测与原生加载记录针对 **1.0.0 / v11**，不是1.0.1的验收结果。1.0.1用相同完整材料、相同问题做小范围前后对照，第一轮记录见[前后对照](../../evals/speak-human/results/concision-1.0.1.json)，第二轮记录见[中间版本结果](../../evals/speak-human/results/concision-1.0.1-final.json)。两轮仍主动扩写，所以随后删除了重复和促使扩写的指导；1.0.1正文的结果见[1.0.1结果](../../evals/speak-human/results/concision-1.0.1-release.json)。

同题测试中，Claude从1.0.0的944字降至1.0.1正文的291字，所需原因、修法及未实现状态保留；仍多写了未问的备选方案。DeepSeek为276字，但没有明确交代测试环境证据和未实现状态。记录保留这些缺口，不将“变短”直接记为完整验收通过。

## 1.0.0 的设计与历史评测

v4—v11 是1.0.0的开发记录，不是发布版本号。

## 这版要达到的表达

**保留容易查阅的结构，在结构里用完整、自然的句子讲清依据和因果。** 用户已明确偏好 B 的结构，同时要求改善自然度、补上理论支撑。Skill 据此采用：

- 问题有多个方面时，用少量有意义的小标题或加粗引导；每项仍然是一段能独立理解的话。
- 把“证据说明什么、机制为何如此、因此应该怎么做”连接起来。理论用于解释成立条件，不装饰术语，也不编造依据。
- 使用中文句法，保留 HTTP、API、Redis、具体代码符号；需要解释的是术语的作用，而不只是中文全称。
- 区分解释/决策和完整改写/交接。后者逐条保留指令，在对应步骤保留原文中的批准、停止和验收条件。
- 已清楚的原文、用户指定的详细程度、机器可读格式，都优先于压缩。说明工作结果不减少实际工作。

这是一个独立的 SKILL.md，不要求 CONTEXT.md、其他 Skill 或某个模型 CLI。Humanizer、no-ai-slop、wait-what 等是调研来源，不是运行依赖。

## 最新测试支持什么

| 项目 | 实际结果 | 能说明什么 |
|---|---|---|
| 新的离线协作发布案例 | Claude、Gemini、DeepSeek 各生成普通精简提示与 Skill 两个回复，共6份；匿名交换 A/B 位置后，6次评审均选择 Skill | 评审器偏好其结构与因果说明；用户后来指出展示仍冗长，此结果不能代替用户验收 |
| 最终版本严格 JSON | Claude、Gemini、GLM、DeepSeek，4/4可直接解析，均为指定3个字符串字段 | 输出格式契约通过；不把解析成功当作内容正确的证明 |
| 实际安装入口 | Claude Code 真正调用 Skill，回传正文与当时的1.0.0文件一致，随后生成缓存问题解释 | 测到了已安装 Skill 的实际加载和回答，不只有文本注入 |
| 本地安装 | 10个现有技能目录均指向仓库同一个文件 | 修改同步生效；没有逐一验证10个 Agent 的交互入口 |

最新比较的样本是**1个独立编写的新案例、3个模型**；A/B换序增加的是位置偏差检查，不增加独立样本量。评审器是 Claude，按用户的结构、自然度和因果支撑偏好判断；没有做真人阅读速度实验。

旧的七模型、四案例测试有55/56份可用回复，27组配对偏好为 Skill 12胜、普通精简提示10胜、5平。后来查出全局上下文干扰，因此这些只能算现有配置下的表现。v9 的另一个新商业案例也没有一致胜出：DeepSeek两次选Skill，Gemini两次选普通提示，Claude一次普通提示、一次平局。以上反例均保留，不能只用最后一组结果宣称所有场景稳定更好。

## 保真仍有具体未通过项

可读性偏好与事实正确分别判定，**严格保真尚未全部通过**。

- Gemini 的长操作交接反复省略“叶澄取得客户书面确认后另开批次”的部分条件；v11 仍遗漏负责人/书面确认，并漏掉 `--rate 20` 的单位解释。该输出不能直接作为操作手册使用。
- 离线案例中，Claude把未测组合可能出现说成“680名巡检员里必然包含”，并断言试点现场必有人未升级；原文没有这两个事实。Gemini开头把先同步旧队列称为“清空离线数据”，虽然后文解释为上传完成，这个表达仍可能误导操作。DeepSeek未保留服务器30天历史的恢复边界。
- 已清楚通知的反向测试中，Claude仍会添加“系统维护”和“以免内容丢失”，原文未提供这些信息。v10的针对性修改没有消除这项失败。不能把“删掉套话”的要求当作已经获得了最小改动保证。

**历史结果的适用范围：评审器曾偏好解释、结果汇报和方案沟通中的结构，但用户反馈表明简洁目标尚未得到充分体现。包含审批、恢复、停止条件的长交接，必须对照原文逐条核对，不能把简洁流畅当作保真通过。** 这些边界来自实际失败，不是泛泛的免责声明。

## 调研与方法的纠正

第一轮交付过早。本轮增加了长上下文、独立编写的新案例、逐项事实审查、负向控制、匿名配对及换序、仅接收答案的代理读者测试，并多次根据失败调整 Skill。评审模型有时会把“不会改变推荐方向”的错误判成轻微问题；作者没有因此把它们记成正确。

新会话不等于隔离全局规则。Grok的基线曾尝试自动加载已经安装的Skill；OpenCode的 `--pure` 只关闭外部插件。清理子进程配置和技能发现后，Gemini小任务的输入降到328 tokens，而原配置约5万。Claude使用安全模式、无工具/技能、明确的中性系统提示。Grok的系统覆盖探针仍有约3.2万tokens，因此未纳入干净对照。所有凭据和全局设置保留原样。

GLM在较长任务中有进程正常退出、但只返回 `step_start` 的失败；DeepSeek也有一例。它们记录为运行失败，不参与偏好计票，也没有被替换成别的模型。Claude原生加载测试曾因排除了用户设置而返回 `Unknown skill`，恢复用户技能发现后，最终版本真实加载通过；失败记录仍在本地原始日志。
